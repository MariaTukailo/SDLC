## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ (Software Design Description, SDD) описывает архитектуру, структуру компонентов и дизайн веб-приложения «Evently». Документ предназначен для команды разработчиков, которая будет реализовывать систему, а также для сопровождающего персонала (для понимания устройства системы при дальнейшей поддержке). 

Документ опирается на ранее согласованную спецификацию требований (SRS), где описано, *что* должна делать система, а SDD отвечает на вопрос, *как* она будет устроена технически.

### 1.2 Область применения {#12-subject-scope}

Веб-приложение «Evently» (Версия 1.0) предназначено для создания и совместного планирования мероприятий. Система построена по клиент-серверной архитектуре с разделением на слои. Клиентская часть реализована как одностраничное приложение (SPA) на React. Серверная часть реализована на Spring Boot по паттерну MVC (Controller-Service-Repository) и предоставляет REST API. База данных (PostgreSQL) взаимодействует с сервером через ORM (Hibernate). Такое разделение обеспечивает независимость слоев, упрощает тестирование и позволяет в будущем заменить любой компонент без переписывания остальной системы.

### 1.3 Определения, акронимы и сокращения {#13-definitions-acronyms-and-abbreviations}

Для однозначного понимания документа в настоящем разделе приведены основные термины и сокращения (расположены в алфавитном порядке):

## 2. Обзор дизайна {#2-design-overview}

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

В проекте «Evently» можно выделить следующих ключевых стейкхолдеров и их интересы, связанные с архитектурой:
* **Разработчики:** Заинтересованы в понятной модульной структуре, четком разделении слоев (Frontend/Backend) и удобстве сопровождения кода.
* **Заказчик:** Заинтересован в том, чтобы архитектура обеспечивала выполнение функциональных требований (создание комнат, чек-листы) и была экономически эффективной (использование Open Source технологий).
* **Конечные пользователи (Организаторы и Гости):** Заинтересованы в высокой скорости работы приложения (быстрая загрузка страниц) и надежности (сохранность данных о мероприятии).

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

Для описания архитектуры системы были выбраны следующие точки зрения, которые наилучшим образом адресуют задачи стейкхолдеров и соответствуют текущему этапу разработки (MVP):

#### 2.2.1 Контекст {#221-context}
**Адресует:** границы системы и внешние зависимости.
Система «Evently» взаимодействует со следующими внешними сущностями:
* **Пользователь:** взаимодействует через браузер (ввод данных, просмотр).
* **Внешние API:** Яндекс.Карты (для отображения места проведения), SMTP-сервер (для отправки email).

#### 2.2.2 Композиция {#222-composition}
**Адресует:** разделение ответственности и модульность.
Система разделена на три основных компонента:
1. **Frontend (SPA на React):** отвечает за пользовательский интерфейс.
2. **Backend (REST API на Spring Boot):** содержит бизнес-логику и обработку запросов.
3. **База данных (PostgreSQL):** отвечает за хранение и целостность данных.

#### 2.2.3 Логическое представление {#223-logical}
**Адресует:** статическую структуру дизайна и абстракции.
На бэкенде используется паттерн MVC (Model-View-Controller). Основные классы абстракций: сущности `Entity` (User, Event, Task), сервисы `Service` (обработка бизнес-логики) и контроллеры `Controller` (прием HTTP-запросов). На фронтенде используются функциональные React-компоненты.

#### 2.2.4 Физическое представление {#224-physical}
**Адресует:** физическую топологию и ограничения.
На этапе MVP физическая инфраструктура представлена одним виртуальным сервером (VPS), на котором развернуты Docker-контейнеры. Отдельные физические серверы для базы данных или балансировщики нагрузки не предусмотрены.

#### 2.2.5 Структура {#225-structure}
**Адресует:** внутреннюю организацию компонентов.
Бэкенд-приложение организовано в виде пакетов: `controller`, `service`, `repository`, `entity`. Это обеспечивает слабую связанность (low coupling) и высокую связность (high cohesion) внутри каждого слоя.

#### 2.2.6 Зависимости {#226-dependency}
**Адресует:** потребности в интеграции и приоритизацию.
Frontend зависит от Backend (через REST API). Backend зависит от Базы данных (через Hibernate/JPA) и от внешних API (Карты, Музыка). Направление зависимостей строго контролируется: контроллеры вызывают сервисы, сервисы вызывают репозитории.

#### 2.2.7 Информация {#227-information}
**Адресует:** структуру данных и их связи.
Основные сущности базы данных: `Users` (пользователи), `Events` (мероприятия), `Tasks` (задачи чек-листа), `Guests` (гости), `Budget` (бюджет). Связи реализованы через внешние ключи (например, одна комната `Event` имеет множество задач `Tasks`).

#### 2.2.8 Интерфейс {#228-interface}
**Адресует:** взаимодействие через контракты.
Внешние интерфейсы системы описаны в спецификации SRS (раздел 3.1). Основным интерфейсом является REST API (JSON), через который Frontend получает данные от Backend. Также используются интерфейсы внешних API (Яндекс.Карты, Spotify).

#### 2.2.9 Взаимодействие {#229-interaction}
**Адресует:** последовательность сообщений в рантайме.
Типовой сценарий взаимодействия: Пользователь нажимает кнопку «Создать комнату» на фронтенде -> React отправляет POST-запрос на Backend -> Контроллер принимает запрос, вызывает Сервис -> Сервис сохраняет данные в БД и возвращает ID комнаты -> Frontend перенаправляет пользователя на страницу комнаты.

#### 2.2.10 Алгоритм {#2210-algorithm}
**Адресует:** логику обработки операций.
Специфические сложные алгоритмы в системе отсутствуют. Вся логика сводится к стандартным CRUD-операциям (создание, чтение, обновление, удаление) и простым проверкам (валидация полей, проверка прав доступа).

#### 2.2.11 Динамика состояний {#2211-state-dynamics}
**Адресует:** эволюцию состояний системы.
Основные состояния в системе связаны с мероприятием: «Запланировано», «В процессе», «Завершено». Также задачи в чек-листе имеют состояния: «Не выполнено», «В работе», «Выполнено». Переход между состояниями задач осуществляется вручную пользователем.

#### 2.2.12 Параллелизм {#2212-concurrency}
**Адресует:** синхронизацию и потоки.
На уровне архитектуры используется многопоточность Spring Boot (обработка нескольких HTTP-запросов одновременно). Специфических требований к синхронизации потоков (например, блокировок) для MVP не предусмотрено, так как пользователи редактируют разные комнаты.

#### 2.2.13 Паттерны {#2213-patterns}
**Адресует:** повторно используемые решения.
В проекте применяются следующие паттерны: **MVC** (Model-View-Controller) для бэкенда, **Repository** (для работы с БД), **DTO** (Data Transfer Object) для передачи данных между слоями, а также **Компонентный подход** во фронтенде (React).

#### 2.2.14 Развёртывание {#2214-deployment}
**Адресует:** отображение компонентов на узлы.
Все компоненты (Frontend, Backend, База данных) развертываются на одном сервере (VPS). Frontend раздается через Nginx (или статический сервер). Backend и БД запущены в Docker-контейнерах. Связь осуществляется по внутренней сети Docker.

#### 2.2.15 Ресурсы {#2215-resources}
**Адресует:** использование ограниченных ресурсов.
Основным ограниченным ресурсом является оперативная память сервера (для работы Spring Boot и PostgreSQL). В текущей версии не требуется сложное управление пулами потоков или дескрипторами файлов, так как нагрузка невысокая (до 100 пользователей).

## 3. Проектные представления {#3-design-views}

В данном разделе описаны ключевые проектные представления системы «Evently», которые детализируют архитектуру и служат руководством для реализации. Каждое представление содержит уникальный идентификатор, ссылку на точку зрения из раздела 2.2 и связь с требованиями из SRS.

---

### 3.1 Представление: Схема базы данных

* **ID**: VIEW-001-DataModel
* **Title**: Логическая и физическая схема базы данных
* **Viewpoint**: Информация (раздел 2.2.7)
* **Representation**: 
  База данных реализуется на PostgreSQL. Основные сущности и их атрибуты:
  * **users** (id, email, password_hash, name, role, created_at);
  * **events** (id, title, description, date, dress_code, location, organizer_id);
  * **tasks** (id, event_id, title, status, deadline, assigned_to);
  * **guests** (id, event_id, name, rsvp_status);
  * **bbudget_items** (id, event_id, title, planned_amount, actual_amount). Примечание: реализация в MVP отложена по согласованию с Заказчиком.
  * **playlist_tracks** (id, event_id, track_name, added_by). Примечание: реализация в MVP отложена по согласованию с Заказчиком.
  * **wishlist_items** (id, event_id, item_name, author_id).
  
  Связи: `events` имеет связь «один-ко-многим» с `tasks`, `guests`, `budget_items`, `playlist_tracks`, `wishlist_items`. `users` связан с `events` (как организатор) и с `tasks` (как ответственный).
  
* **More Information**: Реализует требования REQ-FUNC-001, REQ-FUNC-003, REQ-FUNC-004, REQ-FUNC-005. Соответствует решению из ADR о выборе PostgreSQL. Схема создается автоматически через Hibernate (Spring Data JPA) на основе Entity-классов.

---

### 3.2 Представление: Слои Backend (MVC)

* **ID**: VIEW-002-BackendLayers
* **Title**: Структура слоев серверной части
* **Viewpoint**: Композиция (раздел 2.2.2), Логическое представление (раздел 2.2.3)
* **Representation**: 
  Серверная часть на Spring Boot разделена на 4 уровня:
  1. **Controller:** классы с аннотацией `@RestController` (EventController, TaskController, UserController). Принимают HTTP-запросы, валидируют входные данные (DTO) и возвращают JSON.
  2. **Service:** классы с аннотацией `@Service` (EventService, TaskService, AuthService). Содержат бизнес-логику, проверку прав доступа и вызов репозиториев.
  3. **Repository:** интерфейсы, наследуемые от `JpaRepository` (EventRepository, TaskRepository). Обеспечивают доступ к БД.
  4. **Entity:** Java-классы, маппящиеся на таблицы БД (User, Event, Task, Guest).
  
  Направление вызовов строго сверху вниз: Controller -> Service -> Repository -> Database.
  
* **More Information**: Реализует требования REQ-FUNC-001, REQ-FUNC-007. Соответствует решению из ADR о выборе Spring Boot. Обеспечивает слабую связанность (low coupling) и высокую связность (high cohesion).

---

### 3.3 Представление: Компоненты Frontend

* **ID**: VIEW-003-FrontendComponents
* **Title**: Структура клиентской части (React)
* **Viewpoint**: Композиция (раздел 2.2.2), Структура (раздел 2.2.5)
* **Representation**: 
  Клиентская часть организована следующим образом:
  * **pages/**: Экраны приложения (DashboardPage, RoomPage, LoginPage).
  * **components/**: Переиспользуемые UI-элементы (Header, Footer, TaskCard, GuestList, MapWidget).
  * **api/**: Модули для отправки HTTP-запросов к Backend (axios-инстансы, методы `createEvent`, `getTasks`).
  * **context/**: Глобальное состояние авторизации пользователя (AuthContext).
  
  Взаимодействие: Пользователь взаимодействует с `pages`, которые вызывают `api` для получения данных и передают их в `components` для отображения.
  
* **More Information**: Реализует требования REQ-INT-001, REQ-INT-002, REQ-INT-004. Соответствует решению из ADR о выборе React. Используется React Router для навигации между страницами.

---

### 3.4 Представление: Внешние интеграции

* **ID**: VIEW-004-ExternalIntegrations
* **Title**: Взаимодействие с внешними сервисами
* **Viewpoint**: Контекст (раздел 2.2.1), Взаимодействие (раздел 2.2.9)
* **Representation**: 
  Backend интегрируется со следующими внешними сервисами через HTTP-запросы (RestTemplate/WebClient):
  1. **Яндекс.Карты API:** GET-запрос для получения координат и отображения карты. Ответ обрабатывается и передается на Frontend (виджет `MapWidget`).
  2. **SMTP-сервер:** отправка email-приглашений при создании гостя (через JavaMailSender).
  3. **Google Calendar API:** формирование ссылки для добавления мероприятия в личный календарь пользователя.
  Все ключи API хранятся в переменных окружения (файл `.env`).
  
* **More Information**: Реализует требования REQ-INT-010, REQ-INT-011, REQ-INT-012. Соответствует ограничениям из SRS (п. 2.3) и разделу «Внешние интерфейсы» (п. 3.1.3).

### 4.1 Выбор СУБД PostgreSQL

* **ID**: DEC-001-Database
* **Title**: Использование реляционной СУБД PostgreSQL для хранения данных
* **Context**: Приложению необходимо надежно хранить связанные данные (пользователи, мероприятия, задачи, гости, бюджет). Требуется поддержка транзакций (ACID) и строгих связей между таблицами.
* **Options**: 
  1. PostgreSQL
  2. MySQL
  3. MongoDB (NoSQL)
* **Outcome**: Выбран вариант **«PostgreSQL»**, потому что он обеспечивает строгую типизацию, отлично работает со связанными данными (One-to-Many, Many-to-Many) и имеет зрелую интеграцию со Spring Data JPA (Hibernate).
* **More Information**: Ссылка на полный документ ADR-001. Реализует требования REQ-FUNC-001, REQ-FUNC-004.

---

### 4.2 Выбор бэкенд-фреймворка Spring Boot

* **ID**: DEC-002-Backend
* **Title**: Разработка серверной части на Java с использованием Spring Boot
* **Context**: Требуется создать надежное, безопасное и масштабируемое REST API для обработки бизнес-логики приложения (авторизация, работа с комнатами и задачами).
* **Options**: 
  1. Java + Spring Boot
  2. Node.js + Express
  3. Python + Django
* **Outcome**: Выбран вариант **«Java + Spring Boot»**, потому что фреймворк предоставляет встроенные механизмы безопасности (Spring Security), удобную работу с базой данных через JPA и высокую производительность. Наличие строгой типизации в Java снижает количество ошибок на этапе компиляции.
* **More Information**: Ссылка на полный документ ADR-002. Реализует требования REQ-SEC-002, REQ-INT-013.

---

### 4.3 Выбор фронтенд-библиотеки React

* **ID**: DEC-003-Frontend
* **Title**: Разработка клиентской части (SPA) на библиотеке React
* **Context**: Необходимо создать быстрый, интерактивный и адаптивный пользовательский интерфейс, который будет плавно обновляться без перезагрузки страницы (например, при добавлении задач в чек-лист).
* **Options**: 
  1. React
  2. Vue.js
  3. Angular
* **Outcome**: Выбран вариант **«React»**, потому что он позволяет создавать переиспользуемые компоненты (карточки, формы), обеспечивает высокую скорость рендеринга благодаря Virtual DOM и имеет самое большое сообщество разработчиков, что упрощает поиск решений.
* **More Information**: Ссылка на полный документ ADR-003. Реализует требования REQ-INT-001, REQ-INT-002.
